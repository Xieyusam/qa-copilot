## 触发方式
用户要求"review 代码"、"检查完成情况"、"代码审查"时执行此流程。

## 执行步骤

### 第零步：确定 review 范围
检查是否为 git 仓库：
```bash
git rev-parse --is-inside-work-tree
```
- **是 git 仓库**：执行 `git diff HEAD` 获取变更，优先 review 变更部分
- **不是 git 仓库**：进行全量 review

### 第一步：加载 spec 文档
读取 `.trae/specs/<当前MVP>/` 下的三件套作为评审基准。

### 第二步：任务完成情况核查
检查 `tasks.md` 中标记 `[x]` 的任务：
- 确认代码**真实存在且功能完整**
- 识别"虚假完成"：
  - 文件不存在
  - 函数体为空/只有 `pass`/`TODO`
  - 只有接口定义没有实现
  - 实现与描述不符

### 第三步：需求覆盖检查
对照 `requirements.md`，检查：
- 边界条件：大小限制、格式校验、超时
- 错误场景：网络失败、数据库异常
- 空状态处理：空列表、空知识库
- 并发与竞态

### 第四步：代码质量评审
**前端（TypeScript/Vue）**：
- 类型准确性，避免 `any`
- 组件职责单一，props 完整
- 异步处理 loading/error 状态
- 内存泄漏风险（定时器、事件监听、SSE）
- 魔法值提取为常量

**后端（Python/FastAPI）**：
- 类型注解完整
- 异常处理合理（不过于宽泛）
- 数据库连接正确关闭
- 依赖注入合理
- 关键路径有日志

**通用**：
- 函数超过 50 行需说明原因
- 重复代码是否应抽取
- 注释准确无过时

### 第五步：静态检查（只报告不修改）
运行已有 lint 工具（eslint、ruff、mypy 等），检查：
- 未使用的 import/变量
- 未使用的依赖
- 死代码/死文件
- 调试语句（console.log、print）

### 第六步：单元测试覆盖检查
评分维度（0-10分）：
| 维度 | 说明 |
|------|------|
| 正常路径覆盖 | happy path 测试 |
| 异常路径覆盖 | 错误场景测试 |
| 边界条件覆盖 | 空值、临界值测试 |
| Mock 合理性 | 只隔离外部依赖 |
| 测试独立性 | 无执行顺序依赖 |

检查要点：
- 列出测试文件及数量
- 找出无测试的关键模块
- 识别"测试造假"
- 检查 property-based test 策略

## 输出格式

### 📋 Review 范围
说明增量/全量 review，列出涉及文件。

### ✅ 已确认完成的任务
任务编号 + 简述。

### ⚠️ 疑似虚假完成
任务描述 + 问题位置 + 具体原因。

### 🐛 代码质量问题
按文件列出：`[严重度] 问题描述`

### 🧹 冗余清理候选
未使用 import/变量/依赖/死代码 + 位置。

### 🧪 测试覆盖缺口
评分表 + 未覆盖场景 + 建议补充用例。

### 📊 总结评分
| 维度 | 评分 | 说明 |
五个维度评分 + 优先修复建议。
